# Session 03 | Sentences and paragraphs

## What you should be able to do
Build a paragraph around one supported claim and revise ambiguous wording.

## Preparation and session plan
Recall the key definition and one example from the previous session before continuing. Allow about 75 minutes, including an independent attempt and correction. This is a proposed study session, not a university timetable.

## Core notes and worked example
A useful sentence makes its actor, action and object clear. Prefer a concrete verb: "The program validates the input" is clearer than "Input validation is carried out by the program." Passive voice is still useful when the action or result matters more than the actor, as in a method description.

A paragraph develops one main point. It often begins with a topic sentence, follows with explanation or evidence, and ends by connecting the point to its purpose. Every sentence should contribute to that point. Split paragraphs when the subject changes.

Worked example: "We tested it and it was okay" becomes: "The program correctly classified 0, 50 and 100 as valid marks. It rejected -1 and 101. These boundary tests support the input-range check; they do not establish that every possible input is handled correctly." Notice the limited, precise claim.

Editing pass: remove repeated ideas, vague "this" references, unnecessary introductions and unexplained abbreviations. Keep qualifications that affect meaning. Shorter is useful only if the result remains accurate.

## Reasoning in more depth
A paragraph should advance a clear point. State the claim, provide evidence or a concrete example, explain how that evidence supports the claim, and connect to the next step. A transition is useful when it expresses a real relationship such as cause or contrast. Vague pronouns, unexplained abbreviations and several unrelated claims make a paragraph difficult to follow even when the grammar is correct.

## Independent task | Attempt before reading the answer
Revise: The computer was bad and it did not work so we changed it and it was better. Use a hypothetical observed symptom without claiming a confirmed root cause.

## Worked answer and marking points
Example revision: During the demonstration, the application stopped responding after opening the sample file. Restarting the application restored interaction, but we did not establish the cause. We recorded the file name and steps for a repeat test. The revision distinguishes observation, action, result and remaining uncertainty; it does not turn a restart into proof of a hardware fault.
